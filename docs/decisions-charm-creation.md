# 饰品制作链路决策记录

## 已确认

| 结论 | 理由 |
| --- | --- |
| 本轮只重做管理员制作饰品模板的链路；玩家成长与构筑功能保持现状，后续单独开发。 | 用户明确选择制作模板链路，并要求保留成长与构筑。 |
| 制作流程参照 ILS：游戏内用 Lore 工具制作物品，`/qc export <id>` 导出模板，`/qc give <id> [player]` 按 ID 发放。 | 用户提供 ILS 的 `/lore`、`/ils export`、`/ils give` 实际工作流作为目标。 |
| 新模板不保存 `type` 配置；只从物品 Lore 匹配 `gui.yml` 中配置的槽位 `type`。显示名不参与类型判断。 | 用户明确要求不加 type 配置，只读 Lore，并与 GUI type 匹配。 |
| 新模板的 Lore 必须且只能命中一种 GUI 槽位类型；缺少或命中多个类型时拒绝导出。 | 用户确认类型标记来自 Lore，并选择多类型时拒绝导出。 |
| 导出文件只写物品本体、启用状态和默认权限；需要时可手动补充玩家等级和职业限制，其他值使用全局默认。 | 用户选择新模板只保留物品、权限、等级、职业这类必要信息。 |
| 成功导出后立即重新加载模板，无需手动 `/qc reload`；导出的手持物仍签名，可直接装备。 | 用户明确选择导出后立即可用。 |
| 同 ID 文件默认拒绝覆盖，使用 `-f` 才覆盖。 | 用户明确选择显式覆盖。 |
| 保留旧 `config.yml` 饰品定义、旧 `qcItems` 文件读取、签名识别和玩家存档格式。旧文件显式设置的 `type` 继续有效。 | 用户要求保持旧配置读取与签名识别，并避免存档/API 不兼容。 |
| 启用中的 `config.yml` 同 ID 定义与新导出冲突时拒绝导出。 | 现有加载逻辑让 `config.yml` 定义优先；拒绝冲突可避免新模板写入但不生效。 |

## 迁移与兼容

- 新导出格式不再写入 `charm.type`、`equip-lore` 或空的 `requirements` 节点。
- 老格式仍由现有加载器读取；`type` 缺失的旧文件改为按 Lore 唯一识别 GUI 类型。
- 玩家物品签名、玩家数据文件和公开 API 不变。
- 构筑职责与配置目标见 [`plugin-boundaries.md`](plugin-boundaries.md)，不属于本轮饰品制作链路改动。

## 待定问题

- 无。本记录对应用户确认的本轮实施范围。
